Overview

One pipeline, four capabilities

A Next.js client talks to a FastAPI backend over JSON, multipart, and SSE. Document text and its vector embeddings live together in a single PostgreSQL + pgvector datastore.

Choose extraction

Text (PyMuPDF), OCR (YOLOv8 + Tesseract), or Vision (page images → LLM) — selected per upload.

Embed locally

fastembed (ONNX, CPU) turns chunks into 384-d vectors. No embedding API key, no GPU, no torch.

Retrieve with pgvector

A single indexed cosine query over an HNSW index returns the top-k nearest chunks per document.

Generate & cite

Claude answers from retrieved context with [p.N] citations; OpenAI takes over on failure.

Architecture

System design at a glance

Thin API controllers delegate to focused services. Ingestion runs off the request path as a background task; the LLM layer is provider-agnostic behind one interface.

Request lifecycle

From upload to streamed answer

Two flows compose the product: ingestion runs once per document; query runs on every question.

Ingestion background task
1

Upload

POST /documents stores the file, inserts a row with status=processing, returns 201, and schedules process_document.

2

Extract

The selected extractor (Text / OCR / Vision) returns a list of pages, each tagged with its page number.

3

Chunk

Pages are split into ~1000-char overlapping chunks, preserving the source page for citations.

4

Embed & store

fastembed produces 384-d vectors; chunks + embeddings are bulk-inserted and status flips to ready.

Query SSE stream
1

Embed the question

The same model encodes the question with its query encoder for an apples-to-apples comparison.

2

Top-k retrieval

pgvector returns the nearest chunks by cosine distance; the sources event is emitted first.

3

Prompt & generate

Retrieved text is framed with [p.N] markers and streamed through Claude → OpenAI fallback.

4

Stream & log

delta events carry tokens; a final done event reports provider, tokens, and latency to query_logs.

Inside the code

The two functions that matter most

Retrieval is one indexed query; resilience is one fallback loop that never tears a streamed answer.

services/vectorstore.pyPython
def search(db, *, owner_id, document_id, query_embedding, k):
    # cosine distance via the pgvector <=> operator
    distance = Chunk.embedding.cosine_distance(query_embedding)
    stmt = (
        select(Chunk, distance.label("distance"))
        .where(Chunk.owner_id == owner_id,
               Chunk.document_id == document_id)
        .order_by(distance)   # HNSW index
        .limit(k)             # default top-k = 5
    )
    return [RetrievedChunk(...) for row in db.execute(stmt)]
services/llm/router.pyPython
def stream(self, *, system, messages):
    for i, provider in enumerate(self._ordered()):
        started = False
        try:
            for chunk in provider.stream(...):
                started = True
                yield chunk
            return
        except Exception:
            # once bytes are sent, never switch providers
            if started: raise
            continue   # else fall back to OpenAI
Data model

Chunks: relational rows and vectors together

The chunks table is both the source of truth for extracted text and the vector index used for retrieval — so there is no second store to keep in sync.

The retrieval query

SELECT * FROM chunks
WHERE owner_id = :owner
  AND document_id = :doc
ORDER BY embedding <=> :q   -- cosine
LIMIT :k;                -- HNSW

Related tables

  • users — email, hashed password, active flag
  • documents — filename, extraction_method, status, page/chunk counts, error
  • query_logs — question, provider_used, model, input/output tokens, latency_ms
